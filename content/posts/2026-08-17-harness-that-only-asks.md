## 발표가 끝나고 들은 말

[앞 글](/posts/planning-layer-broke)에 적은 발표를 하고 나서 이런 피드백을 받았다.

> 애초에 AI를 통해 기획 출력물의 수준이 높았다면 아무 불만이 없었을 것이다. 하네스를 적절하게 도입하면, 첫 단계에서 AI가 추론으로 명세서를 쓰고 사람이 막연하게 통과시키는 걸 막을 수 있다.

솔직히 처음엔 발표를 잘못 들은 반응인 줄 알았다. 나는 출력물 품질 얘기를 한 게 아니었으니까. 그래서 다음 발표에서 이 오해를 어떻게 막을지부터 생각하고 있었다.

며칠 지나고 다시 보니 아니었다. 이 말은 설계자가 도메인을 배워서 게이트를 만들려고 하지 말고 AI가 설계를 스스로 보완하게 하라는 거였다. 내 결론이랑 정면으로 다른 노선이다.

그리고 이쪽이 맞는 구석이 있다. 기획, 디자인, 의료, 회계를 나 혼자 다 배울 수는 없다. 발표에서 개발이 아닌 분야일수록 더 심하다고 말한 순간 내 처방이 확장되지 않는다는 걸 스스로 인정한 셈이었다.

## 그대로 받으면 더 나빠진다

다만 그대로 적용하면 깨진다. 내가 관측한 게 정확히 그 자리이기 때문이다.

AI가 설계를 보완하게 하면 보완된 설계는 더 그럴듯해진다. 그러면 사람은 더 안 본다. 고장이 두 종류로 나뉘는데 출력물이 나빠서 받는 사람이 못 쓰는 고장은 품질을 올리면 해결된다. 출력물이 그럴듯해서 아무도 안 보는 고장은 품질을 올리면 악화된다. 피드백은 앞을 보고 말했고 내가 겪은 건 뒤였다.

## 채우게 하지 말고 공격하게 한다

그래서 피드백을 그대로 받지 않고 한 군데를 틀기로 했다. AI가 설계를 채우게 하지 말고 공격하게 한다. 같은 모델이고 같은 지식인데 출력의 형태만 바꾸는 거다.

지금은 이렇게 나간다.

> 현재 코드에는 배송 시작 후 취소 처리 로직이 없습니다. 배송 시작 전까지만 취소 가능하도록 제한하는 것을 권장합니다.

바꾸면 이렇게 나가야 한다.

> 배송이 이미 시작된 주문은 어떻게 됩니까? 기획서에 없습니다.
> 환불 시점이 정의되지 않았습니다. 카드 취소와 포인트 환급 중 무엇이 먼저입니까?

앞은 기획자한테 승인이 남고 뒤는 작성이 남는다. 승인은 안 하고 넘어가면 그냥 통과다. 작성은 안 하면 멈춘다.

## 하네스라는 말

여기서 하네스라는 말이 나온다. 원래 마구를 뜻하는데 AI에서는 모델을 감싸서 입력과 출력과 다음 단계를 통제하는 코드를 가리킨다. 모델은 안 건드리고 어디로 갈지만 정한다.

프롬프트에 "답을 제안하지 마세요"라고 쓰면 모델은 대체로 지키다가 가끔 어긴다. 부탁이니까. 하네스는 부탁하지 않고 답을 넣을 칸을 없앤다.

지금 실패를 이 층에서 다시 보면 고칠 데가 명확해진다. 묻는 역할은 지시해뒀는데 출력에 답을 넣을 자리가 열려 있었다. 그러니까 모델이 채운 거다.

```json
{
  "questions": [{
    "id": "string",
    "question": "string",
    "why_it_matters": "string",
    "evidence": "string",
    "blocks": "boolean"
  }]
}
```

없는 필드가 있는 필드만큼 중요하다. `suggested_answer`나 `recommendation` 같은 건 넣지 않는다. 있으면 모델은 반드시 채운다. `evidence`는 코드나 기획서의 어느 대목을 보고 물었는지인데 이게 있어야 기획자가 질문을 무시하기 어렵다.

그리고 명세서 작성 단계를 아예 다른 호출로 떼기로 했다. 지금은 명세서 쓰기와 누락 지적이 한 호출에 묶여 있는데 명세서를 쓰려면 빈칸을 메워야 하니까 모델이 메운다. 드러내는 일과 메우는 일을 한 호출에 두면 늘 메우는 쪽이 이긴다.

```ts
const blocking = questions.filter((q) => q.blocks).slice(0, 5);
const ready = blocking.every((q) => {
  const a = answers[q.id];
  return a && a.author_type === 'human' && a.text.trim().length > 0;
});

if (!ready) halt('명세서 작성 전에 답해야 할 질문이 남아 있습니다');
```

## 이걸로도 안 막히는 것

아직 안 만들었다. 설계만 해둔 상태다. 그리고 만들어도 못 막을 게 세 개 보인다.

다섯 칸에 전부 "해당 없음"이라고 쓰면 통과된다. 채워졌는지는 검사하지만 그 답이 좋은지는 모른다.

기획자가 AI한테 물어서 붙여넣는 것도 못 막는다. 빈칸을 만들어놔도 그 빈칸을 AI로 채우는 걸 파이프라인 안에서 막을 방법이 없다.

제일 곤란한 건 어떤 질문을 필수로 둘지 정하는 일이다. 그게 곧 좋은 기획이 뭔지를 정하는 일이라 앞 글에서 막혔던 자리가 여기서 또 나온다.

## 반복되는 질문을 기준으로 올린다

그래도 하나는 건졌다.

코드에는 팀이 몇 년간 쌓은 합의가 있어서 기준을 미리 쓸 수 있었다. 기획에는 그게 없어서 미리 못 썼다. 그런데 질문 로그가 쌓이면 나중에는 쓸 수 있다. 같은 질문이 열 번 반복해서 나왔다는 건 매번 비어 있는 칸이라는 뜻이니까.

분기에 한 번 질문 로그를 훑고 자주 나오는 질문을 기획서 필수 항목으로 올린다. 올라간 항목은 애초에 기획 단계에서 채워지니까 다음부터는 질문에 안 나온다. 목록이 그만큼 짧아지고 남은 자리에 새 질문이 들어온다.

발표에서 못 찾았던 선순환이 이 모양인 것 같다. 내가 도메인을 통째로 배울 필요는 없다. 파이프라인이 매번 걸려 넘어지는 자리를 모아두면 그게 기준이 된다. 기억해야 하는 쪽이 내 머리에서 로그로 옮겨가니까 낯선 분야여도 굴러간다.

일단 기획 한 건으로 먼저 돌려볼 생각이다. 거기서 나온 질문 목록을 피드백 준 사람한테 그대로 보여주려고 한다. 노선이 갈렸던 지점이라 같은 화면을 보고 얘기하는 게 말로 설득하는 것보다 빠를 것 같다.
